# 文案与三层排版规范

本规范用于 `oil-diff` 步骤 2：将原始 `diff-data.json` 转化为非代码作者也能迅速读懂的 `report-spec.json`。上级流程见 [SKILL.md](../SKILL.md)。

## 一、 核心北极星：面向项目负责人与协作者汇报

汇报页的读者往往熟悉项目的业务目标，但没有逐行参与当前改动。如果读者打开页面后看到满屏文件列表、自造术语或脱离项目语境的泛泛空话，汇报就直接失效。

归纳事项时遵循「按业务目的聚合，不按文件罗列」：

1. 将一次或多次提交涉及的改动文件聚合成 **3～7 件独立的业务事项**；
2. 每个改动文件都必须被至少一件业务事项覆盖（脚本会强校验 100% 覆盖率）；
3. 同一事项中的核心代码/规则文件放在改法要点（`points`）下，其余顺手同步修改的外围文件归入该章底部的关联文件汇总抽屉（`related-files`）。

## 二、 通用文案四条铁律

### 1. 标题与速览必须写明「所属业务模块/工具 + 具体动作 + 机制变化」

- **错误写法（丢失业务归属）**：`不同用途的网页，使用不同的设计说明`、`先把截图缩放到同一比例，再裁同一块比较`。读者看完不知道改的是哪个模块、哪个脚本还是哪套文档。
- **正确写法（明确保留业务与架构定语）**：
  - `产品工作区的评审流程：合并重复检查，让视觉评审与 UX 走查同时开始`
  - `截图工具 shoot.mjs 的拼图功能：先按共有元素缩放，再裁同一块并排比较`
  - `规则文件结构：按四类页面分别路由到对应的设计规范`
- **保留准确的业务与架构词汇**：像“文件结构、路由、领域入口、产品工作区、视觉评审、UX 走查、组件与等宽数字、自动化测试”这类准确表达业务概念的词汇必须保留，只剔除生造的内部简称。
- **顶部速览目录（`overview`）**：每一条都写成带编号的**完整清楚句子**，完整交代改了哪块业务与具体动作，不要缩成意思含糊的四字词。

### 2. 把内部自造简称翻译为具体动作

- 代码或文档作者常在内部发明简写（例如把“拍几张连续动作的截图”叫“序列图”，把“检查页面”叫“取证/复核”）。
- 撰写汇报文案时，如果必须提到专有概念，第一次出现时用人话点明它的实际动作（例如：`视觉评审（看画面）和 UX 走查（点页面试用）`），绝不直接拿生僻简称串联整句话。

### 3. 缩短句子时严禁删掉「原来怎么做」的前提

- 只有先讲清楚“以前要经历什么繁琐步骤或存在什么缺陷”，读者才能理解“现在改成什么样”的价值。
- 每章的 `problem` 字段用 1～2 句平实的话讲清原来的做法和具体麻烦；紧接着用 `example` 字段给出一个一句就能懂的日常具体场景（例如：`比如参考图的侧边栏宽 240 px，而我们的截图里只有 120 px。先以参考图为准把截图放大 2 倍，再裁出同样的首屏区域，才看得出字号和留白的差别。`）。

### 4. 平实直叙，拒绝公关辞令与参数黑话

- 禁止使用“史诗级、赋能、闭环、全方位、丝滑演进、架构跃迁”等夸张修辞。
- 禁止在页头写对外行科普整个项目是什么的套话（如“本仓库是一套帮助 AI 制作网页的工具……”），页头 `summary` 直接用一两句话概括当前范围改了哪几块核心业务。
- 禁止把命令行参数或变量名直接当成句子的核心动词（如不要写“通过 `--frames` 和 `matchWidth` 完成对齐”，要写“填写两侧共有元素的像素宽度后，工具会自动计算缩放比例”）。
- 一条改法要点（`point`）只讲一件事，不把两件不相关的改动硬塞进同一句话。

## 三、 消除重复与界面噪音

1. **禁止要点正文与文件条摘要“说车轱辘话”**：
   - 当某个改法要点（`.change-point`）下面**只挂载了 1 个文件**时，上方的要点标题和正文（`.point-copy`）已经把改法讲清楚了，下方的文件条**不显示 `.file-explanation`**，直接呈现为紧凑单行：`[文件图标] 路径/文件名 …… +N −M  ▸`。
   - 只有当同一个要点下挂载了 **2 个及以上不同文件**时，才为每个文件提供一句简短的角色说明（`role`，控制在 8～22 字，说明该文件在这一步里各自负责什么）。
2. **禁止外围关联文件刷屏复读**：
   - 当某章存在顺手同步修改的外围文件时，不要平铺十几个大号卡片，也严禁使用兜底模板句在每个文件上重复印同一句话。
   - 渲染器会自动将章内未被要点直接引用、但属于本章 `fileIds` 的文件收进章底的单个 `<details class="related-files">` 汇总条（如 `查看同步修改的其余 N 份关联文档`）。
3. **禁止在文件条与文件树上堆砌机械元信息**：
   - 文件条与右侧文件树只展示文件图标、路径/文件名与 `+N −M` 行数，不展示“最近一轮提交 · 已提交修改”“展开原文对照”“核心原文 · 第 X 行”等废话。

## 四、 清爽三层排版结构（无横线切割、无框套框）

- **第一层（大分区：独立章节书页卡 + 业务胶囊）**：左侧由 1 张首屏总览卡 + N 张独立业务章节卡（`.paper-card`）组成，卡片之间靠 `22px` 的 `32px` 网页网格画布留白自然分区，不把所有章节塞进同一个长白框里画横线切割。
- **第二层（章内叙事：无框背景痛点与例子 + 可视化主舞台）**：章节标题下方直接用干净的无框正文排版写出 `problem` 与 `example`（不套米色方框，章内不画满宽 `border-top` 分割线），紧接着展示本章唯一的 HTML/CSS 可视化对比舞台。
- **第三层（改法要点 + 右侧抽屉触发条）**：`1 / 2 / 3` 要点靠留白自然排列，每个要点下挂载轻量文件触发按钮（`button.diff-file`），点击后从页面右侧滑出 `div` 抽屉查看双栏代码对照。

```json

  "title": "这次修改了哪 N 件事",
  "summary": "一两句话概括本轮修改聚焦的核心业务方向与解决的主要痛点。",
  "relatedTitles": {
    "2": "查看同步修改的其余 {count} 份关联文档"
  },
  "fileVariants": {},
  "items": [
    {
      "number": 1,
      "module": "工作区评审",
      "navLabel": "评审流程",
      "title": "产品工作区的评审流程：合并重复检查，让视觉评审与 UX 走查同时开始",
```
